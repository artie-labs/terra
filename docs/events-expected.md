# Events: what the docs say should happen

One row per file in `pg/events/`. "Emits" is what Postgres logical replication
puts on the wire, "Artie" is what Artie's docs say, "Destination after" is what
the destination should look like once the next row change has landed. Keys in
parentheses are rows in [sources.md](sources.md). Observed behavior on the
subscriber stand-in is in [events-observed.md](events-observed.md).

| # | Event | DDL | Postgres logical replication emits | Artie's docs say | Destination after |
| --- | --- | --- | --- | --- | --- |
| 01 | Weigh-in | `ALTER TABLE animals ADD COLUMN weight_kg numeric(6,2)` | Nothing for the DDL itself (pg-lr-restrictions). The next row change on `animals` carries the new column; a subscriber whose table lacks it errors until the column is added, and additive changes should go to the subscriber first (pg-lr-restrictions). | DDL does not appear in the WAL; with lazy schema evaluation "the new column will not appear in the destination until a DML event occurs on that table" (artie-postgres). New columns are added automatically (artie-schema-evolution). | `animals.weight_kg` exists; the 20 rows the event updates have values, the rest are NULL. |
| 02 | A pangolin is sighted | `ALTER TYPE animal_species ADD VALUE 'pangolin'` | Nothing for the type change. The INSERT that uses the value is sent as text; a subscriber whose enum lacks the label fails with an invalid-input error and stops until fixed (pg-lr-subscription, pg-lr-conflicts). The value cannot be used in the same transaction that adds it (pg-altertype). | Not documented. The typing page covers numbers, JSON and time, not enums (artie-typing). | One new animal, id 900001, species `pangolin`. |
| 03 | The herd outgrows int | `ALTER COLUMN animal_id TYPE bigint` on `animals` and `observations` | Nothing for the rewrite. Values are sent as text, so an int subscriber column keeps working until a value above 2147483647 arrives (pg-lr-subscription). The event inserts animal 3000000001. | The reconciliation job "does not [...] change the type of an existing destination column" (artie-schema-evolution). "Artie uses the destination schema as a source of truth" and raises an error on a lossy conversion (artie-typing). What happens to the 3000000001 row in a 32-bit destination column is not documented. | Both `animal_id` columns 64-bit; animal 3000000001 and observation 9000000001 present. |
| 04 | The collars come online | `CREATE TABLE collar_pings (...)` | Nothing for the CREATE. Because the publication is FOR ALL TABLES the new table is published immediately, "including tables created in the future" (pg-createpublication). The subscriber must create the table and run `ALTER SUBSCRIPTION ... REFRESH PUBLICATION`, which also copies the existing rows (pg-altersubscription, pg-createsubscription). The bigserial sequence is not replicated (pg-lr-restrictions). | Destination tables are created automatically when missing (artie-schema-evolution). New source tables are picked up "every weekday at 6am PT" when auto-replicate is on (artie-tables); otherwise the table has to be added to the pipeline by hand. | `collar_pings` table with 12 seed pings plus everything stream.py has written since. |
| 05 | The naming committee | `ALTER TABLE animals RENAME COLUMN name TO display_name` | Nothing for the rename. Columns match by name (pg-lr-subscription), so the next row change fails on the subscriber with "missing replicated column: display_name" until it renames too; the worker retries the same transaction (pg-lr-conflicts). | The reconciliation job "does not rename columns" (artie-schema-evolution). The notification lists a column removed and a column added (artie-schema-changes). Default behavior of the sync for a rename is not documented. | Expected: `display_name` added and populated from the next change on; `name` stays, frozen, unless "Enable hard deletes for columns" is on, in which case it is dropped after a 4 hour window (artie-schema-evolution). |
| 06 | Rangers file structured reports | `ALTER TABLE observations ADD COLUMN field_report jsonb` | Same as 01: nothing for the DDL, the next row carries the column as text (pg-lr-restrictions, pg-lr-subscription). | Column added automatically; JSON kept "exactly as they appear in your source, with no flattening" (artie-schema-evolution, artie-typing). | `observations.field_report` present; 25 back-filled rows plus every new observation carry an object with ranger, weather, group_size, verified. |
| 07 | Survey adds elevation | `ALTER TABLE watering_holes ADD COLUMN elevation_m int NOT NULL DEFAULT 0` | Nothing for the DDL; the default is stored in the catalog, existing rows are not rewritten and no row images are emitted for them (pg-altertable). The UPDATE in the event emits all 12 rows. An extra subscriber column is filled from its own default (pg-lr-subscription). | Column added automatically; the notification reports "default value, and not-null constraint" changes (artie-schema-evolution, artie-schema-changes). Whether the destination gets the constraint or default is not documented. | `watering_holes.elevation_m` with the 12 surveyed values. |
| 08 | Status moves to the collars | `ALTER TABLE animals DROP COLUMN status` | Nothing for the drop. Rows sent afterwards omit `status`. A subscriber that still has it NOT NULL with no default rejects every INSERT (pg-lr-subscription, pg-lr-conflicts); UPDATEs and DELETEs still apply. | "For safety reasons, columns are not automatically dropped." With hard deletes for columns enabled, Artie marks the column on the first row that omits it, watches for 4 hours, then drops it (artie-schema-evolution). | By default `animals.status` is still there with each row's last value; new rows have NULL. |

## Comment fixes made while writing this table

- `pg/init/01_schema.sql` says `animal_id` is "widened to bigint in migration
  step 3" and `name` is "renamed to display_name in migration step 5". Both match
  events 03 and 05 and were left as is.
- `pg/README.md` (before the rewrite) said "A bare ADD COLUMN is not itself a WAL
  event. Touch a row in that table after the DDL to make the schema change
  visible to a streaming consumer." That matches artie-postgres and was kept.
- The event files were written against this table, so no event comment needed
  correcting; where a behavior is not in Artie's docs the comment says so.
